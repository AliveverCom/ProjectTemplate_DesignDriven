# 1 General

This document defines the project directory structure for the "{PlatformName}" platform, applicable to the entire code repository.
All developers (including AI developers) must follow this plan when creating and organizing files.

<a id="c1-1"></a>

## 1.1 Directory and File Naming Rules

| Scope | Naming Style | Example |
|------|---------|------|
| All `docs/` directories and files | **snake_case** | `{component_code_name}/`, `{component_code_name}_tech_design.md` |
| Technical-design **volumes** (a large design split by chapter or topic) | `{component_code_name}_tech_design_{volume}.md`, `{volume}` a snake_case short name (`runtime`, `interfaces`, `build`, `validation`, `test_cases`, `deviations`, `engine_facts`, `changelog_archive`) | `kernel_tech_design_runtime.md`; platform `tech_*` documents split the same way, e.g. `tech_testing_verification_kpi.md` |
| All backend code directories and files (`src/backend/`) | **snake_case** | `{component_code_name}/`, `source_media_handler.go` |
| All frontend code directories and files (`src/frontend/`) | **kebab-case** | `{component-code-name}/`, `source-media-list.tsx` |
| `ui_page_design/` subdirectories | Free format | `P{nn}  {PageName}/` (generated by a third-party tool, snake_case not required) |
| `ai_dev_history/` subdirectories | **Numbered + PascalCase** | `01_DocReviewRefine/`, `02_DevPlanAndReport/` |

> **Exception**: generic filenames such as `VERSION`, `README.md`, `.gitkeep` remain unchanged and are not subject to the rules above.

> For identifier naming conventions (class names, variable names, column names), see [naming_convention.md](docs/naming_convention.md).

# 2 Top-Level Directory Structure

The top level of the project repository contains only the following:

```
{ProjectName}/
├── .github/                        # CI/CD configuration
├── .gitignore                      # Git ignore rules
├── README.md                       # Project description
├── project_directory_plan.md       # This document: project directory plan
├── docs/                           # Project documentation (see §3)
├── templates/                      # Document templates (platform-level / component-level / mmd / ai_dev)
├── src/                            # All source code (see §4)
├── deployment/                     # Build artifacts and runtime environment
└── {src_old_projects_migration}/   # Legacy project data migration tool (optional)
```

| Directory | Purpose | Committed to Git |
|------|------|-----------|
| `docs/` | {All design documents and development process records} | Yes |
| `templates/` | {Document templates, copied from here when creating new documents} | Yes |
| `src/` | {All source code and contracts} | Yes |
| `deployment/` | {Deployment configuration and runtime environment} | {Yes; except files containing secrets} |

# 3 Documentation Directory (docs/)

<a id="c3-1"></a>

## 3.1 Organizing Principles

| # | Principle |
|---|------|
| 1 | The **`docs/` root directory** holds **platform-level documents** — cross-component documents for the entire platform (business overview, technical overview, technical architecture diagrams, various design specifications, version plans, etc.). The exact number of files grows as the project evolves and is not enumerated exhaustively in this plan |
| 2 | Under **`docs/components/`**, create an independent subdirectory for each **product component**; each component directory contains the standard documents: `{component}_business_desc.md`, `{component}_tech_design.md`, `{component}_uiux.md`, `{component}_version_plan.md`, plus `.mmd` / `.png` diagrams sharing the same name prefix |
| 3 | Under each component directory, create a **`ui_page_design/`** subdirectory to hold the UI design files for all pages of that component. **One folder per page**, named with the page number plus page name (e.g., `P01  {PageName}/`); each page folder contains the **HTML** and **PNG** versions of that page's design. The page flow diagram `{component}_page_flow.mmd/.png` is also placed in this directory |
| 4 | The **`docs/` root directory**, **`docs/common_lib/`**, and **each component directory under `docs/components/`** all get an **`ai_dev_history/`** subdirectory, holding all process records (review, dev_plan, debug, raw_prompts, etc.) generated while using the AI development mode in that module. This directory **separates development process records from formal project documentation**. It is further organized into category subdirectories internally; the templates and directory structure are in `templates/ai_dev/` |
| 5 | If a component has **submodules / daemon processes**, create a `sub_{submodule_name}/` subdirectory for each submodule, containing that submodule's design documents |
| 6 | If a component involves **legacy system migration**, create an `old_projects_migration/` subdirectory holding the migration plan and legacy system technical notes |
| 7 | When a technical design (or a platform `tech_*` document) grows large (rule of thumb: > 100 KB), split it into a **main document** (section 1.0 file index, core concepts, stubs for moved chapters) and **volumes** `{component_code_name}_tech_design_{volume}.md`. Volumes keep the main document **chapter numbers (globally unique)**, have the same authority level and their own version numbers; cross-document references still read "`{component_code_name}_tech_design section x.y`" and are resolved through the 1.0 index. Old change-log rows go to a `_changelog_archive` volume. Purpose: AI agents and review instances read only the volume they need. Behavioural facts of a third-party engine live in the `_engine_facts` volume (`EF-nn` ids) and are cited, never re-verified in the engine source |

# 4 Source Code Directory (src/)

<a id="c4-1"></a>

## 4.1 Organizing Principles

| # | Principle |
|---|------|
| 1 | `src/` contains all directories related to source code: frontend, backend, API definitions, gateway configuration, authentication configuration, deployment configuration, and scripts |
| 2 | The **frontend** uses a {pnpm workspace Monorepo} structure; all product components share the same build configuration and common libraries |
| 3 | The **backend** supports both {Language A} and {Language B}; common libraries are maintained separately per language |
| 4 | **API definitions** are centralized in `src/api/`, serving as the **single source of truth (contract)** for frontend/backend development |
| 5 | Both frontend and backend are organized internally as "**common libraries + product components**" |
| 6 | Each component directory is **created only when that module actually enters development**; do not pre-create empty directories during the planning phase (frontend exception: a placeholder `VERSION` may be added in advance) |

```
src/
├── frontend/                   # Frontend Monorepo
├── backend/                    # Backend services
├── api/                        # OpenAPI definitions (centralized)
├── gateway/                    # API gateway configuration
├── auth/                       # Authentication and permission configuration
├── deploy/                     # Deployment configuration (Docker / K8s, etc.)
└── scripts/                    # Build, development, and ops scripts
```

<a id="c4-2"></a>

## 4.2 Frontend Directory Structure

The frontend uses a **{pnpm workspace Monorepo}** structure; all product components share the same build configuration and common libraries.

```
src/frontend/
├── packages/
│   ├── shared/                 # Frontend common library (UI components, utility functions, type definitions)
│   │   └── VERSION
│   ├── common-lib/             # Common library frontend (business components reused across components)
│   │   └── VERSION
│   ├── {unified-portal}/       # Unified portal frontend (framework, menus, dashboard)
│   │   └── VERSION
│   ├── {component-code-name}/  # {ComponentName} frontend
│   │   └── VERSION
│   └── …
├── package.json                # Monorepo root configuration
├── {pnpm-workspace.yaml}
├── tsconfig.base.json          # Shared TypeScript configuration
├── {vite.config.shared.ts}     # Shared build configuration
└── {.eslintrc.js}
```

**Internal structure of a single component package** (created only once that module's frontend development begins):

```
packages/{component-code-name}/
├── src/
│   ├── pages/                  # Page components, one directory per page, matching the P{nn} in the uiux document
│   ├── components/             # Components reused within this package
│   ├── services/                # API client wrappers (api.ts)
│   ├── models/                 # TypeScript type definitions (C/E/I prefixes)
│   ├── stores/                 # State management, one store per business entity
│   ├── mock/                   # Hardcoded mock data (used during v0.1)
│   └── routes.tsx              # Route registration, consistent with the "Route Definitions" section of the uiux document
└── VERSION
```

**Notes**:

- `packages/shared/` holds UI components, HTTP wrappers, permission utilities, and type definitions reused across components.
- `packages/common-lib/` holds **business** components reused across components, corresponding to `docs/common_lib/`.
- Frontend package names use **kebab-case** (see §1.1).
- {Each component's frontend package is bundled independently, dynamically loaded or routed to at runtime by the Portal / or bundled together as a single SPA — fill in based on the actual choice}.

## 4.3 Backend Directory Structure

The backend supports {Language A} and {Language B}; common libraries are maintained separately per language.

```
src/backend/
├── shared/                            # Backend common libraries
│   ├── {py-shared}/                   # {Language A} common library (DB connections, logging, auth middleware)
│   │   └── VERSION
│   └── {go-shared}/                   # {Language B} common library
│       └── VERSION
├── {component_code_name}/             # {ComponentName} backend
│   └── VERSION
└── …
```

**Internal structure of a single backend service** (created only once that module's backend development begins):

```
src/backend/{component_code_name}/
├── cmd/                        # Entry programs, one subdirectory per executable
│   ├── {component}_api/        #   REST API service entry point
│   └── {daemon_name}/          #   Daemon entry point (if any)
├── config/                     # Configuration files and config structs
├── internal/
│   ├── handler/                # HTTP layer: parameter parsing, validation, response wrapping, route registration
│   ├── service/                # Business logic layer, transaction orchestration
│   ├── repository/             # Data access layer (SQL / ORM)
│   ├── model/                  # Data structure definitions (C-prefixed classes)
│   ├── enum/                   # Enum definitions (E prefix)
│   └── mock/                   # Hardcoded mock data (used during v0.2)
├── pkg/                        # Utilities that can be referenced externally (unified response structures, etc.)
├── sql/                        # Database creation scripts, migration scripts, sample data
│   ├── init_databases.sql
│   ├── migrations/
│   └── sample_data.sql
└── VERSION
```

**Notes**:

- `shared/{py-shared}/` and `shared/{go-shared}/` are the common libraries for the two languages respectively, containing database connection management,
  unified logging, authentication middleware, error handling, and common data models.
- Layer responsibility boundaries are defined in [technical_overview.md](docs/technical_overview.md) §1.3; **cross-layer calls are prohibited**.
- Each component may freely choose its implementation language; the choice is recorded in `technical_overview.md` §3.

<a id="c4-4"></a>

## 4.4 API Definition Directory

All product components' OpenAPI definitions are centralized in `src/api/`, serving as the **single contract** for frontend/backend development.

```
src/api/
├── {component_code_name}/      # {ComponentName} API definitions
│   └── openapi.yaml
├── …
└── shared/                     # Common schemas (data structures reused across components)
    └── common-schemas.yaml
```

**Notes**:

- Each component's OpenAPI definition is maintained independently, versioned alongside the component's iterations.
- `shared/common-schemas.yaml` holds data structures reused across components (pagination parameters, unified response bodies, error structures, etc.).
- {The frontend auto-generates TypeScript types and API client code from the OpenAPI definitions}.
- A human-readable summary of the endpoint list is in `docs/APIs/api_endpoint_list.md`; the two must stay consistent.

# 5 Per-Component Versioning

<a id="c5-1"></a>

## 5.1 Strategy

This platform adopts a **multi-component independent versioning** strategy (Per-Component Versioning).
This is a common practice in multi-component, cross-language Monorepos; the core ideas are as follows:

| # | Point | Description |
|---|------|------|
| 1 | **Each independently releasable unit has its own `VERSION` file** | Including each component's documentation, frontend package, backend service, and common libraries. The file content is a **single plain-text line containing the version number** (e.g., `0.0.0`), with nothing else |
| 2 | **Version number format** | Follows the `vA.B.C.D.E` specification defined in `docs/version_plan.md`. The value in the `VERSION` file **has no `v` prefix** (`0.0.0`, not `v0.0.0`) |
| 3 | **Independent evolution** | Each component iterates at its own pace — documentation may be at `0.2`, the frontend already at `1.0.3`, the backend still at `0.2.5`. Components are **not required to keep version numbers in sync** |
| 4 | **Git tag naming rule** | When releasing a specific version of a component, tag it using the `{layer}/{component}/v{version}` format, for example:<br>`docs/{component_code_name}/v0.1`<br>`fe/{component_code_name}/v1.0.1`<br>`be/{component_code_name}/v0.2.3`<br>`be/shared/{go-shared}/v1.0.0` |
| 5 | **CI/CD integration** | Pipelines read each component's `VERSION` file to determine Docker image tags, artifact version numbers, and release changelogs |

<a id="c5-2"></a>

## 5.2 VERSION File Distribution

The table below lists the location and initial value of every `VERSION` file:

| Location | Initial Version | Description |
|------|---------|------|
| `docs/VERSION` | `{0.1.0}` | Overall version of platform-level documentation |
| `docs/common_lib/VERSION` | `{0.0.0}` | Common library documentation version |
| `docs/components/{component}/VERSION` | `{0.0.0}` | Each component's documentation version (× {N}) |
| `src/frontend/packages/shared/VERSION` | `{0.0.0}` | Frontend common library version |
| `src/frontend/packages/{component}/VERSION` | `{0.0.0}` | Each component's frontend version (× {N}) |
| `src/backend/shared/{py-shared}/VERSION` | `{0.0.0}` | {Language A} backend common library version |
| `src/backend/shared/{go-shared}/VERSION` | `{0.0.0}` | {Language B} backend common library version |
| `src/backend/{component}/VERSION` | `{0.0.0}` | Each component's backend version (× {N}) |

> Each component's own version roadmap (what each v0.x does) is written in
> `docs/components/{component}/{component}_version_plan.md`, with the template found at `templates/component/_version_plan.md`.
